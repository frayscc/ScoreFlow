# V2-0 现状核对、数据保护与迁移方案

日期：2026-09-13

## 核对结论

V2 将在现有 V1 上增量实现，不重写识别、计分、报告或 scorepack 主链路。基线回归为 `pytest` 48 项通过、Vite 生产构建通过、npm 高危级别审计 0 项。SQLite 当前 schema 为 v8。

当前目录不是 Git 仓库，没有提交历史或远程，因此没有“旧 Git 历史已泄露真实数据”的问题。GitHub CLI 已登录两个账号，但活动账号明确为 `frayscc`；后续默认在该活动账号下创建 ScoreFlow 公共仓库，若同名冲突再采用项目相关后缀。不会向非用户上游仓库推送。

工作数据目录中存在 37 个无学生的本地项目记录，属于运行/验证残留；它们位于已忽略的 `var/`，不会进入源码提交、GitHub Actions 或 Release。公开前仍会对暂存清单和将发布的 ZIP 再做一次内容及凭据扫描。

用户提供的图标源图已核对为 1254×1254 PNG、带 Alpha 通道，视觉内容符合深蓝/青绿色“积分登记表”方向。V2-4 将以该用户提供素材为母版来源，生成规范的 1024 PNG、ICO、ICNS、iconset 和网页图标，并在来源说明中如实记录，不把它声称为仓库原创矢量。

## V1 已具备且继续复用

- 本地 FastAPI＋React 架构、动态回环端口、会话/CSRF 防护、单实例及安全退出。
- SQLite 版本迁移、名单原子导入、周期快照、纸表唯一身份、补充表及历史冻结。
- PDF/图片批量导入、有界单工作线程、二维码身份、旋转/质量检查、四态识别和人工复核。
- 正反面完整性、采用版本唯一约束、空白面人工确认、事务入账、幂等、防重、撤销、关闭及报告。
- 单项目 `.scorepack` 一致性快照、文件哈希、安全恢复和失败防覆盖。
- PyInstaller macOS arm64 可运行包和 Windows 构建脚本骨架。

## 与 V2 的具体差距

1. 名单解析仍以四列 CSV 为中心，不支持行首学号的混合分隔粘贴、逐行诊断、重名提示或已有名单差异预览。
2. 学生当前必须立即带有效组号；没有可持久化的待分组池、周期草稿分组、拖拽/批量移动、撤销和严格的 49×7 开始门槛。
3. 扫描页只有识别结果列表，没有面向文件/批次的导入记录管理；除队列满时回滚外，没有完整的重试、删除、撤销并移除及共享原件引用清理。
4. 校正图能查看，尚无全页分类叠加层和槽位点击编辑；全空白结果没有专门的核对提示与移除入口。
5. 尚无独立演示项目类型及安全重置。
6. PDFium 的真实 OMR 栅格路径尚未用“页面内容笔迹＋PDF批注外观”构造样本作回归。
7. 用户图标尚未进入源码、网页、ICO/ICNS 或 PyInstaller spec；当前 `.app` 使用默认图标。
8. 当前目录没有 Git 仓库、CI/Release workflow、MIT 许可证、CHANGELOG 或公开发布页面；Windows 脚本也没有被远程 Windows Runner 实际验证。

## 数据库增量迁移方案

迁移继续沿用单调递增的 SQLite schema，不修改已开始/已关闭周期的历史行，不重新分配项目、学生、周期、纸表、识别或账本 ID。

- 名单与分组迁移：允许主名单学生暂时无组；草稿周期提前持久化 `period_students` 的待分组状态和顺序，分组/组长操作只写草稿。开始周期时在同一事务中验证人数、唯一归属、组容量和组长，再冻结现有快照。既有 v8 周期数据原样保留。
- 导入记录迁移：补充页级活动/移除状态和任务代次控制。后台写入必须同时匹配活动任务代次，取消或删除后迟到结果不能复活记录。物理原件仅在没有任何页面引用时清理。
- 演示项目迁移：为项目增加明确类型；重置通过创建新项目 ID 完成，旧二维码不能匹配新演示项目。正式项目没有一键全清入口。
- scorepack 同步升级：新字段进入单项目裁剪、校验、导入表顺序和旧版本迁移测试；恢复后继续保持账本及重复入账约束。

每次结构迁移使用现有事务/外键检查，并增加“v8 实际数据升级到新版本”的回归。实现期间保留 `var/scoreflow.sqlite3`，不使用破坏性重置；发布前通过 scorepack 做一次 V1→V2 往返验证。

## 发布前保护措施

- `.gitignore` 已覆盖 `var/`、`output/`、SQLite、scorepack、构建目录、依赖目录、环境文件和常见临时文件。
- PyInstaller spec 继续使用显式资源清单，不打入工作数据库、扫描件、报告输出或开发凭据。
- Git 初始化前检查待提交文件；首次 push 前检查文件内容和提交对象；Release ZIP 只来自构建后的应用目录。
- CI 的 PR 权限保持只读；只有标签 Release job 使用 `contents: write`，不采用 `pull_request_target` 或自托管 Runner。
